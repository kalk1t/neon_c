## Findings and uncertainty

- Launcher only opens the prebuilt `dist/first-flight/RoadstersRace.exe`; it does not compile or install software.
- Default window is 1440 x 900, with requested vsync, 4x MSAA, and a 60 FPS target. An uncapped frame loop is not established by the source.
- The menu renders the live scene immediately. City generation considers 625 building positions and draws many individual decorative primitives, with distance filtering but no explicit view-frustum filtering or level of detail in this code.
- The full-resolution post shader samples the scene once plus a 5 x 5 glow neighborhood: 26 texture reads per pixel, or about 33.7 million reads per frame at 1440 x 900. Actual cost depends on GPU, caching, compiler, and driver. There is no low-quality startup preset or automatic quality reduction.
- Resizing recreates the render target without checking the new target's validity; rendering also continues while paused or unfocused. These are additional robustness concerns, not a confirmed explanation of this incident.
- Windows System events 41 and 6008 confirm an unclean restart. The queried event set contained no display-reset event 4101, resource-exhaustion event 2004, or bugcheck event 1001. Queried Application events did not show a Roadsters crash report. Absence of a recorded event does not exclude a GPU hang or memory pressure.
- Hardware queries through CIM were denied. No per-frame timing, CPU/GPU utilization trace, or persistent native renderer log from the incident was available in the inspected artifacts.

Heavy rendering is a plausible explanation for lag. The cause of the whole-PC freeze remains unconfirmed; do not label it a proven driver fault, memory leak, hardware limitation, or fixed issue.

Next work should use static analysis and non-graphics validation to prepare bounded rendering defaults, a cheap startup/menu path, optional effects, and persistent diagnostics before any separately authorized graphics run.
